[BLOCKER] TimescaleDB rejects the spec's `id UUID PRIMARY KEY` on both hypertables (verified on 127.0.0.1:55432)
  detail: Running the spec's `electricity_readings` DDL followed by `create_hypertable('electricity_readings','billing_period_start', ...)` on the local PG 15.14 + Timescale 2.28.3 fails with: `ERROR: cannot create a unique index without the column "billing_period_start" (used in partitioning)`. Same for `water_readings` / `reading_date`. The Phase 1 gate 'All Alembic migrations run clean on fresh DB' cannot pass with the schema as written. Secondary verified facts: (1) with `PRIMARY KEY (id, billing_period_start)` the hypertable is created and `INTERVAL '3 months'` on a DATE column becomes a 90-day chunk (fine); (2) `CREATE TABLE fk_probe (r_id UUID REFERENCES electricity_readings(id))` fails with `there is no unique constraint matching given keys` — nothing (e.g. a future `alerts.reading_id`) can FK to a hypertable; (3) the `savera` database already exists with `timescaledb 2.28.3` installed and zero tables, auth is scram-sha-256, user/password `postgres`/`postgres`. Silent-failure modes: an agent 'fixes' the error by dropping the PK entirely (later `ON CONFLICT (id)` upserts in the seed script fail or silently duplicate), or by making `billing_period_start` alone the PK (one reading per date globally), or Alembic autogenerate emits plain `CREATE TABLE` with no `create_hypertable` at all (tests pass, hypertables never exist).
  rec: Adopt composite PKs: `PRIMARY KEY (id, billing_period_start)` and `PRIMARY KEY (id, reading_date)`. Add `UNIQUE (user_id, billing_period_start)` and `UNIQUE (user_id, reading_date)` (both include the partition column, so Timescale accepts them) — these give the seed script and manual-entry endpoint an idempotent `ON CONFLICT (user_id, billing_period_start) DO UPDATE` target. Never reference a hypertable from an FK. Write migrations by hand (no autogenerate): `alembic init -t async` using SQLAlchemy 2.0.54's asyncpg dialect so no second DB driver is needed; `0001_initial.py` runs the DDL via `op.execute(...)` and `op.execute("SELECT create_hypertable('electricity_readings','billing_period_start', chunk_time_interval => INTERVAL '3 months', if_not_exists => TRUE)")`. Add `tests/test_migrations.py`: create a throwaway DB (`savera_test_<pid>`), `alembic upgrade head`, assert `SELECT count(*) FROM timescaledb_information.hypertables` = 2, then `downgrade base` + `upgrade head` round-trip. Local DATABASE_URL: `postgresql://postgres:postgres@127.0.0.1:55432/savera` (tests: `.../savera_test`).
