[HIGH] SPEC 5.2 — compute_baseline / check_anomaly contract (units, std choice, floor, severity), with verified test vectors
  detail: Adopt for backend/app/services/baseline.py. Constants: MIN_SAMPLES=3, THRESHOLD_MULT=1.5, STD_FLOOR_FRACTION=0.10, HIGH_SEVERITY_Z=3.0, ELEC_WINDOW_BILLS=6, WATER_WINDOW_DAYS=90, WATER_MIN_SAMPLES_FOR_ALERTS=14, LPG_WINDOW_CYCLES=6.

`compute_baseline(values: Sequence[float]) -> dict | None`: drop None; if len < 3 return None; mean = statistics.fmean; raw_std = statistics.stdev (SAMPLE, n-1 — with n=3..6 the population formula understates spread by up to 18% (sqrt(2/3) at n=3) and would over-alert; sample std also equals Postgres stddev_samp so SQL and Python agree — verified 76.4285 in both); std_dev = max(raw_std, 0.10*mean) (floor: a flat history [100,100,100] otherwise gives upper==mean and a +1 unit reading is an 'anomaly'; with the floor upper >= 1.15*mean, so the minimum alertable change is +15%; it also makes z-score division safe). Return {mean, std_dev (the FLOORED value — this is what is stored in baselines.std_dev so the schema invariant upper == mean + 1.5*std_dev holds), upper_threshold = mean + 1.5*std_dev, lower_threshold = max(0, mean - 1.5*std_dev), sample_count}, each rounded to 4 dp.

`check_anomaly(current: float, baseline: dict | None) -> dict` returns {is_anomaly, pct_over, severity, direction, z_score}: baseline None -> {False, 0.0, 'none', 'flat', 0.0}; pct_over = round((current-mean)/mean*100, 1) (signed, negative when under — same definition as green_score.pct_over); z_score = round((current-mean)/std_dev, 2); direction = 'over' | 'under' | 'flat'; is_anomaly = current > upper_threshold (strict); severity = 'none' if not is_anomaly else 'high' if z_score >= 3.0 else 'medium'. The function is unit-agnostic: callers pass normalised values.

Units (baseline samples AND `current` must share them): electricity = kWh per 30 days, `kwh * 30.0 / (billing_period_end - billing_period_start + 1)` (inclusive billing_days; validate 1 <= billing_days <= 70 and billing_period_end <= today); water = litres per day (raw daily reading); lpg = kg per day = lpg_cycles.daily_burn_rate of closed cycles.

Sample selection is walk-forward (strictly before the evaluated sample; see contamination finding): electricity `SELECT kwh*30.0/(billing_period_end-billing_period_start+1) FROM electricity_readings WHERE user_id=$1 AND billing_period_start < $2 ORDER BY billing_period_start DESC LIMIT 6`; water `SELECT liters FROM water_readings WHERE user_id=$1 AND reading_date >= $2::date - 90 AND reading_date < $2` (alerts only when >= 14 rows; compute_baseline itself still needs only 3); lpg `SELECT daily_burn_rate FROM lpg_cycles WHERE user_id=$1 AND end_date IS NOT NULL AND end_date < $2 ORDER BY end_date DESC LIMIT 6`. The stored baselines row uses the same queries without the `< $2` predicate (last 6 bills / last 90 days / last 6 closed cycles as of now) and is upserted `ON CONFLICT (user_id, resource_type) DO UPDATE SET mean=EXCLUDED.mean, std_dev=..., upper_threshold=..., lower_threshold=..., sample_count=..., computed_at=now()` after every reading and by the monthly scheduler (1st, 02:00 IST) for users with >= 3 samples; it is a pure function of the reading rows, hence idempotent.

Verified vectors for tests/test_baseline.py and tests/test_anomaly.py: compute_baseline([330,330]) -> None; compute_baseline([330,330,330]) -> {mean 330.0, std_dev 33.0, upper 379.5, lower 280.5, n 3}; check_anomaly(480, that) -> {is_anomaly True, pct_over 45.5, severity 'high', direction 'over', z_score 4.55} (the spec's 480-vs-330 test); compute_baseline([280,300,320,340,360,380]) -> {330.0, 37.4166, 386.1249, 273.8751, 6}; against it check_anomaly(385) -> False (16.7% over but inside 1.5 sigma), check_anomaly(390) -> True/'medium'/z 1.6, check_anomaly(270) -> False/'under'/-18.2; compute_baseline([100,100,100]).upper == 115.0 with 114 -> False and 116 -> True (floor test); kwh_per_30d(238, 2026-03-21, 2026-04-20) == 230.32; calling compute_baseline twice on the same list returns equal dicts and upserting twice leaves one baselines row (idempotency).
  rec: Write the constants and both functions exactly as above, and put every listed vector in the test files before wiring baseline.py to routers/readings.py. Store the floored std_dev; do not store the raw one.

[HIGH] Green Score formula is discontinuous at the mean (100 -> 80), so a stable household oscillates ~22 points on ±1% changes — the seed makes this visible
  detail: Spec 5.4: current <= mean -> 100; mean < current <= upper -> 80 - 80*(pct_over/50); above upper -> max(0, 40 - pct_over). At pct_over -> 0+ the score is 80, not 100, and at the upper boundary (pct_over 15 for a floored std) the two branches give 56 and 25. Replay with the spec formula on the STABLE user: Ananya water May 100, Jun 78.3 (+1.06% over), Jul 100, Aug 78.7, Sep 100; Deepa Sep electricity 79.1 for +0.6%. The dashboard gauge will swing 100 -> 78 -> 100 for a household doing nothing different, which undermines the 'credible government-programme' requirement. 5.4 is locked, so this needs plan-phase sign-off, but it is an algorithm defect, not taste.
  rec: Propose for sign-off a continuous piecewise version that keeps every acceptance test passing (100 at mean, 0 floor, same inputs): band mean..upper: score = 100 - 60 * (current - mean) / (upper - mean) (100 at mean, 40 at upper); above upper: score = max(0, 40 - (pct_over - pct_upper)) where pct_upper = (upper - mean)/mean*100. Whichever formula is chosen, apply the '+5 if improved vs last month' bonus per resource before averaging and cap at 100. Replay numbers with the spec formula are in the seed finding for comparison.

  rec: Keep the spec signature but make tests/test_green_score.py assert the invariance explicitly (documents the design) and apply per-capita normalisation where it matters: compute ward_percentile on total_score (already scale-free) and offer the peer comparison as both 'per household' (ward_aggregates.avg_consumption) and 'per person' (avg_consumption / avg household size — add `avg_household_size FLOAT` to ward_aggregates or compute it in the same query).

[MEDIUM] Duplicate same-day water readings and overlapping bills silently double consumption and fabricate leak alerts
  detail: The schema allows two water_readings rows for one (user_id, reading_date); the daily leak rule sums nothing, but any dashboard/monthly aggregate that sums per day will double, and a second POST of 400 L on a 400 L day looks like 800 L (> upper, >= 1.5x mean) — one more day and leak_suspected fires with a push.   rec: POST /api/v1/readings/water upserts: `INSERT ... ON CONFLICT (user_id, reading_date) DO UPDATE SET liters = EXCLUDED.liters, source = EXCLUDED.source RETURNING id` (verified). [MEDIUM] LPG: one-open-cycle rule, predict_finish testability, and ward LPG aggregate must be rate-based
  detail: (a) `UNIQUE (user_id, end_date)` allows any number of NULL end_dates; the spec defers to the app layer, but `CREATE UNIQUE INDEX uq_lpg_one_open_cycle ON lpg_cycles (user_id) WHERE end_date IS NULL` enforces it in the DB (verified: second open cycle -> duplicate key error) and the API maps that to 409. DECISIONS:
 - Define hypertable primary keys as (id, billing_period_start) and (id, reading_date) and add UNIQUE (user_id, billing_period_start) and UNIQUE (user_id, reading_date) in the first Alembic migration.
 - Compute baselines with sample standard deviation (statistics.stdev / stddev_samp) floored at 10% of the mean, and store the floored value in baselines.std_dev.
 - Normalise electricity to kWh per 30 days with inclusive billing days, keep water in litres per day, and use lpg daily_burn_rate in kg per day for both baseline samples and the current value.
 - Evaluate every reading against a walk-forward baseline built only from samples strictly before it, and treat the baselines table purely as a display/next-check cache refreshed after each reading and monthly.
 - Window sizes are the last 6 bills, the last 90 daily water readings (alerts only from 14 samples), and the last 6 closed LPG cycles.
 - Set severity from the z-score: medium for 1.5σ < z < 3σ, high for z ≥ 3σ, and push FCM only for high electricity anomalies, leak_suspected and LPG refill alerts.
 - Fire leak_suspected on two consecutive logged days each above upper_threshold and at least 1.5× mean, always severity high, suppressed for 7 days after the previous leak alert.
 - Fire water high_consumption in-app only when a single day exceeds upper_threshold and 1.3× mean, and never while a leak alert is active.
 - Fire milestone when a sample is at or below lower_threshold (per bill, per closed LPG cycle, per completed water month) with a 45-day suppression per resource.
 - Add alerts.dedupe_key with UNIQUE (user_id, dedupe_key) and insert every alert with ON CONFLICT DO NOTHING using the key formats in the alert-rules finding.
 - Add UNIQUE (ward_id, resource_type, period_start) to ward_aggregates, store all avg_consumption values per household per 30 days, and flag anomalies at >25% above the mean of the previous three monthly rows.
 - Enforce a single open LPG cycle with a partial unique index on lpg_cycles (user_id) WHERE end_date IS NULL, and give predict_finish a today parameter.
 - Fetch weather with httpx at a 3 s total / 1.5 s connect timeout, single attempt, inside BackgroundTasks only, returning None on any failure so the alert is still written with weather_context null.
 - Use the archive endpoint for periods ending more than 7 days ago and the forecast endpoint with past_days otherwise, request daily=temperature_2m_max with timezone=Asia/Kolkata, and require 70% coverage in both windows.
 - Generate the weather sentence from the mean daily max delta versus the equal-length prior window with a ±1.5 °C threshold and a ≥32 °C hot-day count, applied to electricity high_consumption and milestone alerts only.
 - Seed exactly the three named users, 39 filler households (12 in wards 1–3, 3 in ward 4) and the ward-2 August water ×1.45 spike with the fixed UUIDs, emails, RNG seeds and values listed in the seed finding, anchored on SEED_TODAY = 2026-09-24.
 - Run the alert pipeline chronologically for the three named users only, then recompute baselines, green scores and ward aggregates for everyone, and assert the expected alert inventory with a --verify flag.
 - Cover the electricity anomaly + weather path with an integration test that posts a 480 kWh bill on a synthetic [330,330,330] history rather than relying on seed replay.
